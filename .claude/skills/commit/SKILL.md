# コミット

変更内容を読んで、Conventional Commits 形式の日本語メッセージでコミットする。

```
- [ ] 1. 変更の把握と対象範囲の確定
- [ ] 2. type と粒度の判断
- [ ] 3. メッセージの起案
- [ ] 4. ユーザーへの提示と承認  ← ここまでは履歴に何も作らない
- [ ] 5. コミット実行
- [ ] 6. 確認と報告
```

## 1. 変更の把握と対象範囲の確定

`git status`・`git diff`（未ステージ）・`git diff --staged`（ステージ済み）で実際の変更を把握する。
ステージされている変更があればそれだけを対象とし、無ければ作業ツリーの変更全体を対象とする。

**絶対にコミットしてはいけないもの**（見つけたら対象から外し、ユーザーに報告する）:
- 認証情報（API キー、トークン、`.env`、秘密鍵）
- 巨大なバイナリやデータセット
- `.gitignore` で除外されるべきなのに追跡されてしまっているファイル

## 2. type と粒度の判断

| type | 用途 |
| --- | --- |
| `feat` | 新機能の追加 |
| `fix` | バグ修正 |
| `docs` | ドキュメントのみの変更 |
| `style` | 動作に影響しない整形（空白、セミコロン、フォーマッタ適用） |
| `refactor` | 挙動を変えない内部構造の改善 |
| `perf` | パフォーマンス改善 |
| `test` | テストの追加・修正 |
| `build` | ビルドシステムや依存関係の変更 |
| `ci` | CI 設定の変更 |
| `chore` | 上記のいずれにも当てはまらない雑務 |

判断に迷ったら、**利用者から見て何が変わるか**で選ぶ。使える機能が増えたなら `feat`、
壊れていたものが直ったなら `fix`、外から見て何も変わらないなら `refactor` か `chore`。

**1コミット1目的。** 複数の無関係な変更が混ざっているなら、1つのメッセージに詰め込まず、
コミットを分けることをユーザーに提案する。

## 3. メッセージの起案

```
<type>(<scope>): <要約>

<本文>
```

**1行目（必須）**
- `<type>` は英語小文字。`<要約>` は日本語
- 全体で 50 文字以内を目安にする
- 末尾に句点（。）を付けない
- 「〜を追加」「〜を修正」のように体言止め + 動詞の連用形で終える（「〜しました」のような丁寧語は使わない）

**`<scope>`（任意）**
影響範囲を名詞で書く。ディレクトリ名やモジュール名が目安（例: `feat(api):`、`fix(auth):`）。
リポジトリ全体に及ぶ変更や、範囲が絞れない場合は省略する。

**本文（1行目だけで足りないときに書く）**
- 1行目との間に空行を1行入れる
- 各行 72 文字程度で折り返す
- **何を変えたか（What）と、なぜそうしたか（Why）を書く。どう実装したか（How）は書かない。**
  - What は、変更範囲が1行目に収まらないときに書く。コードを開かずにスコープを掴めることに価値がある
  - Why は diff から復元できない唯一の情報なので、本文の主目的はこちら。
    「他の方法ではなくこれを選んだ理由」「解決しようとした問題」「既知の制約」が書く価値のある内容
  - How を書かないのは、コードを読めば分かることの重複だから。
    **diff をそのまま日本語に訳したような本文（「変数 X を追加し、関数 Y に渡すよう変更」）は書かない。**
    同じ変更でも「年齢の欠損を中央値で補完するよう変更」のように、
    コードの操作手順ではなく変更の意味の水準で書く
- 1行の変更で理由も自明なら、本文は省いてよい

**破壊的変更**
後方互換性が壊れる場合は、type の直後に `!` を付け、フッターに理由を書く。

```
feat(api)!: レスポンス形式を JSON に統一

XML 対応を廃止した。利用者がいないことを確認済み。

BREAKING CHANGE: /v1/users の XML レスポンスは返らなくなる
```

## 4. ユーザーへの提示と承認

起案したメッセージと、コミットに含まれるファイルの一覧を提示して承認を得る。
**ここまでは履歴に何も作らない。**

## 5. コミット実行

複数行メッセージは heredoc で渡す。

```bash
git commit -m "$(cat <<'EOF'
feat(features): 年齢の欠損を中央値で補完する処理を追加

欠損行を捨てると学習データが 2 割減るため、補完を選んだ。
中央値にしたのは年齢分布が右に裾を引いており、平均だと
高齢側に引っ張られるため。
EOF
)"
```

セッションの指示で Co-Authored-By 行が指定されている場合は、本文の末尾に空行を挟んで付ける。

## 6. 確認と報告

```bash
git log -1 --stat
```

コミットが成功したことと、含まれるファイルが意図通りであることを確認して報告する。

---

## やらないこと

- **push しない。** ユーザーが明示的に頼んだときだけ行う
- `--no-verify` を使わない。pre-commit フックが落ちたら、内容を読んで原因を直す
- `git commit --amend` や `git reset` を勝手に使わない。履歴の書き換えは必ず確認を取る
- 空のコミットを作らない。変更がなければその旨を報告して終わる

## 例

```
docs: データ仕様を data/README.md に追加
```

```
fix(predict): 提出ファイルの id が連番になっていた問題を修正

test.csv の id は 0 から始まる連番ではないため、DataFrame の
インデックスをそのまま書き出すと別人の予測として提出されていた。
```

```
chore: 競技データを git 管理外にする .gitignore を追加

SIGNATE の規約によりデータの再配布が禁止されているため。
```
